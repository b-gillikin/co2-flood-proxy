# Prithvi decoder recovery on the Apple GPU

Internal engineering record, 1 November 2026. The native Prithvi Tiny spatial
profile failed because the installed PyTorch2.9.1 MPS backend rejects adaptive
average pooling when feature-grid dimensions are not divisible by a requested
pool size. This is the failure documented in
[PyTorch issue96056](https://github.com/pytorch/pytorch/issues/96056).
The existing CPU forward/backward checks were successful; this was a device
execution problem, not evidence against the model or the input data.

## Implementation

`src/applied_mps_pool.py` preserves the intended adaptive average operation.
Only unsupported non-divisible MPS pools copy their feature tensor to CPU,
apply PyTorch adaptive average pooling and copy the result back. Both copies
remain in autograd. Supported MPS pools and CPU execution retain their native
operation. The replacement is parameter-free and checkpoint keys do not change.
There is no resizing to a more convenient input grid or decoder substitution.

The first repaired forward pass agreed with CPU, but a real training backward
exposed another MPS error: `NativeBatchNormBackward0` attempted an incompatible
view of a non-contiguous tensor. Autograd anomaly tracing localized it to
Prithvi's UPerNet decoder. Decoder BatchNorm pre-forward and backward-gradient
hooks now make those tensors contiguous on MPS. This changes memory layout,
not values, normalization settings, running-statistics policy or model parameters.
The hooks are installed only inside the Prithvi model factory.

The model, published weights, input resolution/bands, decoder, trainable
parameters, optimizer policy, labels and evaluation design remain as specified.
The shared tuning runner fingerprints the compatibility helper and explicitly
records its backend policy. No installed package was modified or upgraded.

## Verification and provenance

The regression tests cover divisible/non-divisible pools, partially unspecified
output sizes, CPU/MPS output and input-gradient agreement, state keys and
optimizer parameter identity. BatchNorm tests cover non-contiguous inputs and
gradients, parameter gradients and running-statistics agreement. All45 targeted
tests passed, including the existing task/preparation tests.

The original failed profile and the two subsequent diagnostic attempts are
preserved. They are engineering failures, not scientific fitted results.
The versioned recovery run is
`results/applied_study_v2/prithvi-mps-recovery-v3/`, generated by
`208_profile_prithvi_mps_recovery.py`. It compares initial CPU/MPS forward
outputs on the same real training batch, then profiles a complete training
epoch with complete batches and finite-gradient checks. It never accesses
validation or test labels and retains no trained head.

Completed profile queues preserve their original source hashes. Later Prithvi
factory repair therefore creates an expected historical source-version
difference; those records are not rewritten as if they used the fix. The
execution auditor continues to reject source drift in an active queue while
allowing recorded historical differences for terminal queues. The ongoing
extraction queue's frozen sources remain unchanged.

Timing includes GPU-to-CPU transfers and contention with Presto. Use the
recovered profile for Prithvi scheduling; do not infer model accuracy from it
or combine CPU/MPS runtime measurements into a universal model speed ranking.

## Completion

The recovered profile completed all189 batches /378 training chips, with finite
gradients throughout. The full training epoch took146.24 seconds (median batch
0.685 seconds); explicit gradient checks add engineering overhead. Initial
CPU/MPS full-model output maximum absolute difference was7.34e-7. Four adaptive
pool modules use the compatibility implementation. No scientific accuracy
result follows from this run. All16 task/learner profile combinations now have
a successful profile, using this versioned replacement for the one original
failed Prithvi profile. The previous failure record remains intact.
